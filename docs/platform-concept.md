# Концепция: платформа «ядро + плагины»

> Статус: черновик концепции, ревизия 2. Кода нет — документ для обсуждения
> архитектуры. Что изменилось относительно ревизии 1 — в конце, в разделе
> «История ревизий».

## Зачем

VKR сейчас — монолитный кабинет преподавателя: группы, занятия, check-in по QR,
журнал оценок, политики оценивания, промежуточная аттестация.

Новое приложение — **универсальная платформа**:

- **ядро** ничего не знает о предметной области (нет «студентов», «групп», «занятий»,
  «предметов»);
- вся предметная логика и все данные живут в **плагинах**, которые пишем мы сами
  и вкомпилировываем в приложение;
- плагины включаются в пространстве через **«маркетплейс»**;
- **каждый плагин приносит свою таблицу** с данными и может **дополнять таблицы
  других плагинов** (колонки, модификаторы баллов).

Учебный процесс становится лишь одним набором плагинов. Проверка концепции —
этот набор должен покрыть всё, что VKR умеет сейчас, без единого «если предмет…»
в ядре.

## Ключевые решения

| # | Решение | Почему |
|---|---|---|
| 1 | Два уровня изоляции: **организация** и **пространство** | Группа одна на несколько предметов; права и политики — на предмет (§1.1). |
| 2 | Плагины — модули модульного монолита (Spring Modulith) | Одна транзакция, одна БД, один деплой; для ВКР — реалистично. |
| 3 | Одна версия кода на всех; версионируются только **настройки** | Плагины вкомпилированы — «разные версии плагина в разных пространствах» невозможны (§2.8). |
| 4 | Ссылки между плагинами — составной FK на `core.entity` (организация + id + тип) | Существование, тип и изоляция проверяются базой, без триггеров (§4). |
| 5 | Права — **гранты с областью** (scope), измерения областей объявляют плагины | Сейчас есть «доступ только к группе X, только практики» — это нельзя потерять (§2.4). |
| 6 | Точки расширения объявляют **плагины**, а не только ядро | Штрафы встраиваются в `grading`, а не в ядро (§2.2). |
| 7 | Все расчёты (штрафы, вклад посещаемости, итог) — на бэке | Один источник правды для таблиц, экспорта и будущего кабинета студента (§6). |
| 8 | PostgreSQL + JSONB | Данные сильно связаны, схемы известны заранее (§5). |

## Общая схема

```
                      ┌──────────────────────── Nuxt (фронт) ─────────────────────────┐
Браузер ──cookie──►   │  оболочка ядра: навигация, маркетплейс, общий <PluginTable>   │
                      │  Nuxt layer на каждый плагин: маршруты, меню, настройки       │
                      └───────────────────────────┬───────────────────────────────────┘
                                                  │ /api/proxy/** (+ JWT)
                      ┌───────────────────────────▼──────── Spring Boot (бэкенд) ─────┐
                      │ ЯДРО                                                          │
                      │  org · space · members/grants · plugin registry ·             │
                      │  entity registry · table framework · extension points ·       │
                      │  event bus (outbox) · аудит · экспорт · публичные маршруты    │
                      ├───────────────────────────────────────────────────────────────┤
                      │ ПЛАГИНЫ (модули, вкомпилированы)                              │
                      │  people · schedule · attendance · check-in · grading ·        │
                      │  penalties · attendance-score · final-assessment · highlight  │
                      └───────────────────────────┬───────────────────────────────────┘
                                                  │
                      ┌───────────────────────────▼──────── PostgreSQL ───────────────┐
                      │ core.*        p_people.*   p_schedule.*   p_attendance.*  …   │
                      └───────────────────────────────────────────────────────────────┘
```

## 1. Ядро

### 1.1 Организация и пространство

В ревизии 1 был один уровень — workspace («кафедра, курс, команда»). На данных
VKR он не работает:

- группа студентов одна, а предметов у неё несколько (`POST /groups/{g}/subjects/{s}`);
- права преподавателя, политики оценивания, check-in — **на предмет**.

Если workspace = предмет, группы дублируются по предметам. Если workspace =
кафедра, некуда положить права и настройки «на предмет». Поэтому уровней два:

| Уровень | Что это в учебном наборе | Что живёт на уровне |
|---|---|---|
| **Организация** (`org`) | вуз / кафедра | пользователи, справочники (люди, группы), администраторы |
| **Пространство** (`space`) | предмет | набор включённых плагинов, их настройки, гранты, рабочие данные (занятия, оценки, посещаемость) |

Ядро не знает слова «предмет»: пространство — просто именованный контейнер.
Каждый плагин объявляет, на каком уровне живут его данные (`level = ORG | SPACE`):
`people` — на уровне организации, `attendance` — на уровне пространства.
Плагин уровня `ORG` может «подключать» свои сущности к пространству (группа ↔
предмет) через ядро — `core.space_entity`.

### 1.2 Компоненты

| Компонент | Назначение |
|---|---|
| **Org / Space** | Границы изоляции данных (§1.1). |
| **Users, Members & Grants** | Пользователи (OIDC, как сейчас), участие в организации/пространстве, гранты прав с областью (§2.4). |
| **Plugin Registry** | Каталог вкомпилированных плагинов, граф зависимостей, что включено в каком пространстве. |
| **Entity Registry** | Реестр «существует сущность X типа T в организации O» — общая точка для ссылок между плагинами (§4). |
| **Extension Points** | Реестр точек расширения и их реализаций; точки объявляют ядро и плагины (§2.2). |
| **Table Framework** | Единый формат таблицы (чтение + запись ячеек), общий фронт-компонент, экспорт (§2.3). |
| **Event Bus** | Доменные события после коммита, с журналом публикаций (Spring Modulith Event Publication Registry = outbox). |
| **Public Routes** | Анонимные маршруты плагинов с ограничением частоты и токенами-«возможностями» (§2.6). |
| Общее | Аудит изменений, экспорт в Excel, i18n, страница «Маркетплейс». |

### 1.3 Таблицы ядра

```sql
core.org            (id, name)
core.space          (id, org_id, name, archived_at)
core.app_user       (id, oidc_sub, display_name)               -- кто входит в систему
core.org_member     (org_id, user_id, role)                    -- role: OWNER | ADMIN | MEMBER
core.space_member   (space_id, user_id)
core.grant          (id, space_id, user_id, permission text,
                     scope jsonb)                              -- scope = NULL → без ограничений
core.space_plugin   (space_id, plugin_id, enabled, settings jsonb,
                     settings_version int, enabled_at, disabled_at)
core.entity         (id uuid, org_id, type text, plugin_id, archived_at,
                     UNIQUE (org_id, id, type))                -- цель составных FK
core.space_entity   (space_id, entity_id)                      -- «группа подключена к предмету»
core.audit          (id, at, user_id, space_id, plugin_id, entity_id,
                     action, before jsonb, after jsonb)
```

«Пользователь» (`core.app_user`) и «участник» (`people.member`) — разные вещи:
первый входит в систему, второй — запись о человеке в журнале. Связь
необязательная (`people.member.user_id`) — так кабинет студента можно добавить
позже, ничего не ломая.

## 2. Контракт плагина

### 2.1 Дескриптор

Плагин — модуль Spring со структурой `web/ domain/ internal/` (как модули текущего
бэкенда) и описанием:

```java
public interface PluginDescriptor {
    String id();                           // "attendance"
    String name();                         // для маркетплейса (ключ i18n)
    String description();
    Level level();                         // ORG | SPACE — где живут данные
    Set<String> dependsOn();               // {"people", "schedule"} — жёсткие
    Set<String> enhances();                // {"grading"} — мягкие: работает и без них
    Set<String> providesEntityTypes();     // {"attendance.mark"}
    Set<String> referencesEntityTypes();   // {"people.member", "schedule.occurrence"}
    Set<PermissionDef> permissions();      // attendance.read, attendance.write (+ какие измерения scope учитывает)
    Set<ScopeDimensionDef> scopeDimensions(); // people: "group", "subgroup"; schedule: "lessonType"
    SettingsSchema settings();             // JSON Schema + текущая версия + мигратор старых версий

    default void onEnable(UUID spaceId) {}
    default void onDisable(UUID spaceId) {}
}
```

Правила:

- свои миграции Liquibase в своей схеме `p_<id>`; накатываются при старте для
  всех, независимо от того, включён ли плагин; данные выключенного плагина
  сохраняются;
- REST под `/api/s/{space}/p/{pluginId}/**` (уровень `ORG` — `/api/o/{org}/p/{pluginId}/**`);
  общий фильтр ядра отвечает 404, если плагин не включён, и проверяет членство;
- данные других плагинов — только через их публичный `*Api`
  (как сейчас `AttendanceApi`, `GradingApi`), никакого SQL в чужую схему.
  Проверяется тестом `ApplicationModules.verify()` (Spring Modulith) и ArchUnit;
- `referencesEntityTypes` должен быть покрыт `dependsOn` (с учётом транзитивных
  зависимостей) — проверяется при старте.

### 2.2 Точки расширения

Ядро не может знать про «штраф за просрочку» — но и `grading` не должен знать
про `penalties`. Решение — точки расширения, которые объявляет **владелец**
данных, а реализуют другие плагины:

```java
// объявляет grading (в своём публичном api-пакете)
public interface ScoreModifier {
    int order();                                                  // порядок применения
    ScoreCell apply(SpaceContext ctx, ScoreCell cell);            // балл → балл (+ пояснение)
}
public interface ScoreContributor {                               // доп. баллы вне заданий
    Map<UUID, Contribution> contribute(SpaceContext ctx, Set<UUID> memberIds);
}

// реализует penalties
@Extension(point = ScoreModifier.class, plugin = "penalties")
class LatenessPenalty implements ScoreModifier { ... }

// реализует attendance-score (мост attendance → grading)
@Extension(point = ScoreContributor.class, plugin = "attendance-score")
class AttendancePoints implements ScoreContributor { ... }
```

Ядро даёт реестр: `extensions.active(ScoreModifier.class, spaceId)` возвращает
только реализации плагинов, **включённых в этом пространстве**. Выключили
`penalties` — модификатор исчез из расчёта, данные и настройки остались.

Точки расширения ядра (общие для всех):

| Точка | Кто реализует | Зачем |
|---|---|---|
| `TableProvider` | плагин с таблицей | своя таблица (§2.3) |
| `ColumnContributor(tableId)` | любой | колонка в чужой таблице: «% посещаемости» в списке группы, «итог» в журнале оценок |
| `ScopeDimension` | `people`, `schedule` | измерения областей прав (§2.4) |
| `ExportContributor` | любой | листы в общем Excel-экспорте |
| `DashboardWidget` | любой | карточка на странице пространства |

### 2.3 Таблицы

Таблица — главный UI платформы, поэтому контракт — не только чтение, но и запись,
секции, фильтры и конкурентное редактирование.

```java
public interface TableProvider {
    String tableId();                                     // "attendance.journal"
    TableResponse read(AccessContext ctx, TableQuery q);   // q: фильтры, секция, страница
    PatchResult patch(AccessContext ctx, List<CellPatch> patches);
}

public record TableResponse(
    List<Column> columns,      // id, title, type, editor, group (секция колонок), source plugin
    List<Section> sections,    // секции строк: группа / подгруппа (как SectionedTable)
    List<Row> rows,            // entityId, sectionId, подписи
    Map<String, Cell> cells,   // "rowId:columnId" → value, display, highlight, editable, version, hint
    Map<String, Object> meta   // итоги, легенда подсветки, применённые политики
) {}

public record CellPatch(String rowId, String columnId, JsonNode value, long expectedVersion) {}
```

- **Типы ячеек** фиксированы ядром: `number(min,max)`, `enum(options)`
  (статусы посещаемости), `text`, `bool`, `computed` (только чтение). Фронт по
  типу выбирает редактор — это то, что сейчас делают `SectionedTable`,
  `useGridCellNav`, `use*Drafts`.
- **Конкурентность:** у ячейки есть `version`; `patch` с устаревшей версией
  возвращает конфликт по этой ячейке, остальные сохраняются. Два преподавателя
  в одном журнале не затирают друг друга молча.
- **Права** применяются провайдером: строки/колонки вне области гранта не
  возвращаются, ячейки вне области записи приходят с `editable=false` (§2.4).
- **Чужие колонки:** ядро склеивает ответ `TableProvider` с колонками от
  `ColumnContributor` текущих включённых плагинов; запись в такую колонку
  уходит её плагину-владельцу.
- **Объём:** таблица группы в VKR — десятки строк × сотни колонок; пагинация по
  секциям (группам), а не по строкам.

### 2.4 Права и области доступа

Сейчас преподаватель получает на предмет либо полный доступ, либо список
областей «группа (+подгруппа) (+тип занятия)». Это обязано пережить переход, но
ядро не знает слов «группа» и «тип занятия». Поэтому:

- **измерения** областей объявляют плагины: `people` — `group`, `subgroup`;
  `schedule` — `lessonType`;
- **грант** = пользователь + право + область:
  `scope = [{"group": "g1", "subgroup": "sg2", "lessonType": "PRACTICE"}, …]`,
  `NULL` — без ограничений (как `allPermissions=true`);
- плагин в дескрипторе указывает, какие измерения учитывает его право
  (`attendance.write` учитывает `group`, `subgroup`, `lessonType`);
- ядро передаёт в провайдеры `AccessContext` с разобранными областями, а
  `ScopeDimension` отвечает на вопрос «входит ли сущность X в значение
  измерения» (`people`: участник ∈ подгруппе; `schedule`: проведение — практика);
- UI выдачи прав (сейчас `PermissionScopeSelect`) строится из списка измерений
  включённых плагинов.

Роли — только сокращения для набора грантов («преподаватель с полным доступом»).
Проверка всегда по грантам.

### 2.5 Взаимодействие плагинов: вызов или событие

| Нужно | Механизм | Пример |
|---|---|---|
| Изменение должно случиться **вместе** с моим | синхронный вызов `*Api` зависимости в той же транзакции | `check-in` при подтверждении пишет статусы через `AttendanceApi` — частичный перенос недопустим |
| Прочитать чужие данные | синхронный вызов `*Api` | `final-assessment` читает баллы через `GradingApi` |
| Сообщить «что-то произошло», реакция не обязательна сразу | событие после коммита (outbox) | `EntityArchived`, `LessonRescheduled` → пересчёт кешей, уведомления |

Направление зависимостей одно: `check-in → attendance`, а не наоборот. Циклы
запрещены (проверяет Modulith).

### 2.6 Публичные маршруты

Check-in уже сейчас работает без входа: студент открывает QR, вводит код
аудитории, ищет себя в списке и отмечается. Контракт:

- плагин объявляет публичные эндпоинты; ядро монтирует их под
  `/api/public/p/{pluginId}/**` вне проверки членства;
- доступ — по **токену-возможности** (id сессии check-in + проверенный код),
  а не по пространству из URL;
- ядро навязывает ограничение частоты и журналирует обращения;
- на фронте — отдельный layout без оболочки дашборда (как `pages/check-in/[id].vue`).

### 2.7 Фронт

- Nuxt layer на плагин: маршруты, пункты меню, форма настроек (генерируется из
  JSON Schema), собственные редакторы ячеек, если базовых не хватает.
- Все layers вкомпилированы; что показывать, решает ответ
  `GET /api/s/{space}/plugins` (включённые плагины + мои права). Middleware
  маршрута плагина отвечает 404, если плагин выключен, — по аналогии с текущим
  `subject-permission`.
- Таблицу рисует общий `<PluginTable>` по `TableResponse` (переиспользуем
  `SectionedTable`, `useGridCellNav`, `use*Drafts`, `use*Export`).
- Типизированный клиент — как сейчас, `@hey-api/openapi-ts` из одного OpenAPI,
  где теги = плагины.

### 2.8 Маркетплейс и жизненный цикл

- Список плагинов: описание, зависимости, статус в пространстве, какие таблицы и
  колонки он добавит.
- **Включить** — проверка `dependsOn` (недостающие предлагаются к включению
  вместе) → `enabled = true` → `onEnable` → настройки по умолчанию.
- **Выключить** — запрещено, пока включены зависящие от него плагины
  (`dependsOn`); `enhances`-плагины лишь теряют функцию. Данные сохраняются.
- **Удалить данные** — отдельное явное действие с подтверждением; блокируется,
  если на сущности плагина ссылаются другие (FK `RESTRICT`).
- **Версии.** Код один на всех, поэтому `version` в пространстве не хранится.
  Хранится `settings_version`: при обновлении плагин поставляет мигратор
  настроек `vN → vN+1`, ядро прогоняет его лениво при чтении или пакетно при
  старте. Схема БД мигрирует Liquibase для всех сразу.

## 3. Набор плагинов «Учебный процесс» (перенос из VKR)

| Плагин | Уровень | Таблица / вклад | Источник в VKR |
|---|---|---|---|
| `people` | ORG | участники × группы/подгруппы; измерения `group`, `subgroup` | `group`, `student`, `subgroup` |
| `schedule` | SPACE | занятия и **проведения**; «активное занятие»; измерение `lessonType` | `lesson`, `lesson_scope` |
| `attendance` | SPACE | участники × проведения, статусы `PRESENT/LATE/ABSENT/EXCUSED` | `attendance` |
| `check-in` | SPACE | сессии и отметки по QR; публичные маршруты | `check-in-sessions`, `CheckInPolicy` |
| `grading` | SPACE | участники × задания; точки `ScoreModifier`, `ScoreContributor` | `assignments`, `grades` |
| `penalties` | SPACE | `ScoreModifier`: штраф/бонус по `lessonsOffset` | `PenaltyPolicy`, `usePenalty` |
| `attendance-score` | SPACE | `ScoreContributor`: баллы за статусы посещаемости | `AttendancePolicy` |
| `final-assessment` | SPACE | колонка «итог» в журнале + своя таблица; допуски заданий | `results`, `FinalAssessmentPolicy`, `useFinalVerdict` |
| `highlight` | SPACE | подсветка ячеек по порогам для любых таблиц | `Grading/AttendanceHighlightPolicy` |

«Предмет» отдельным плагином не нужен: это пространство (§1.1). Подключение
группы к предмету — `core.space_entity`.

Граф зависимостей:

| Плагин | `dependsOn` (жёстко) | `enhances` (мягко) |
|---|---|---|
| `people` | — | — |
| `schedule` | `people` | — |
| `attendance` | `people`, `schedule` | — |
| `check-in` | `attendance` | — |
| `grading` | `people`, `schedule` | — |
| `penalties` | `grading` | — |
| `attendance-score` | `attendance`, `grading` | — |
| `final-assessment` | `grading` | `attendance` (гейт по посещаемости) |
| `highlight` | — | `grading`, `attendance` |

`attendance-score` выделен из `attendance` намеренно: посещаемость без баллов —
нормальный сценарий, и тогда `attendance` не тянет зависимость от `grading`.

## 4. Данные и связи — только в плагинах

Ядро не знает слов «участник», «группа», «занятие». Оно хранит только реестр
сущностей `core.entity`. Всё остальное — в схемах плагинов.

Ссылка на чужую сущность — **составной FK** из трёх колонок: организация, id и
тип. Тип хранится в колонке-константе с `CHECK`, поэтому база сама проверяет,
что `member_id` указывает именно на участника из **той же организации**:

```sql
p_people.member (
  id        uuid PRIMARY KEY,
  org_id    uuid NOT NULL,
  type      text NOT NULL DEFAULT 'people.member' CHECK (type = 'people.member'),
  user_id   uuid NULL REFERENCES core.app_user,   -- для будущего кабинета
  full_name text NOT NULL,
  FOREIGN KEY (org_id, id, type) REFERENCES core.entity (org_id, id, type)
);

p_attendance.mark (
  id             uuid PRIMARY KEY,
  org_id         uuid NOT NULL,
  space_id       uuid NOT NULL REFERENCES core.space,
  member_id      uuid NOT NULL,
  member_type    text NOT NULL DEFAULT 'people.member'       CHECK (member_type = 'people.member'),
  occurrence_id  uuid NOT NULL,
  occurrence_type text NOT NULL DEFAULT 'schedule.occurrence' CHECK (occurrence_type = 'schedule.occurrence'),
  status         text NOT NULL,
  comment        text,
  version        bigint NOT NULL DEFAULT 0,
  FOREIGN KEY (org_id, member_id, member_type)         REFERENCES core.entity (org_id, id, type) ON DELETE RESTRICT,
  FOREIGN KEY (org_id, occurrence_id, occurrence_type) REFERENCES core.entity (org_id, id, type) ON DELETE RESTRICT,
  UNIQUE (member_id, occurrence_id)                            -- одна отметка на участника и проведение
);
```

Остальные таблицы набора — по тому же шаблону (колонки `*_type` опущены):

```sql
p_people.group        (id → entity, name)
p_people.subgroup     (id → entity, group_id, index)
p_people.membership   (member_id, group_id, subgroup_id)       -- «участник ∈ группа» знает только people
p_schedule.lesson     (id → entity, space_id, type, title, active)
p_schedule.occurrence (id → entity, lesson_id, group_id NULL, subgroup_id NULL, date)  -- бывший lesson_scope
p_grading.assignment  (id → entity, lesson_id → entity, max_points, required, admission jsonb)
p_grading.grade       (member_id → entity, assignment_id → entity, points,
                       awarded_lesson_id → entity, version)
```

- **Проведение, а не занятие.** Посещаемость ставится на конкретное проведение
  (дата + группа/подгруппа), как `lesson_scope` сейчас. В ревизии 1 `mark`
  ссылался на `lesson` — это теряло данные.
- **`lessonsOffset` не хранится**, а вычисляется `schedule` по «активному
  занятию» на момент сдачи — тогда перенос занятия корректно меняет штраф.
- Плагин объявляет, на какие типы он ссылается (`referencesEntityTypes`) —
  при старте проверяется, что они покрыты `dependsOn`.
- **Удаление/архивация:** ядро публикует `EntityArchived(id, type)`, зависимые
  плагины реагируют сами (скрывают колонку, исключают из расчёта); FK
  `ON DELETE RESTRICT` не даёт оставить «висячие» ссылки при физическом удалении.
- Цена решения: вставка любой сущности = вставка в `core.entity` в той же
  транзакции. Это одна строка в узкой таблице, индекс по
  `(org_id, id, type)` — для нашего масштаба несущественно.

Следствие: плагин `people` можно заменить другим («команды», «сотрудники»), и
`attendance`/`grading` продолжат работать, пока новый плагин публикует
сущности типа `people.member` и реализует измерения `group`/`subgroup`.
Это стоит проверить на практике — см. §8.

**Альтернатива** — универсальное хранилище в ядре
(`record(type, data jsonb)` + `link(from, to, kind)`). Гибче, но теряются
типизация, ограничения и быстрые агрегаты. Оставляем на случай таблиц, которые
пользователи создают сами без кода (§9).

## 5. PostgreSQL или MongoDB → PostgreSQL (+ JSONB)

- Плагины пишем мы → схемы известны заранее; главное преимущество MongoDB
  (произвольные схемы) здесь не нужно.
- Данные сильно связаны: участник ↔ группа ↔ проведение ↔ оценка ↔ посещаемость.
  Итоговая аттестация — агрегаты по нескольким плагинам; в SQL это JOIN,
  в MongoDB — `$lookup`, денормализация и ручная согласованность.
- Целостность (FK, уникальность «одна отметка на участника и проведение»,
  транзакции) — из коробки. Составные FK на `core.entity` из §4 возможны
  только при проверке ссылок базой.
- Гибкие части (настройки плагинов, области грантов, уровни аттестации, пороги
  подсветки) — JSONB; GIN-индекс только там, где по JSONB ищут (`core.grant.scope`).
- Изоляция: схема на плагин; организация/пространство — колонки `org_id`/`space_id`
  и фильтр в коде. Row-Level Security — вторая линия защиты: `SET LOCAL
  app.org_id` в начале каждой транзакции (не на соединение — пул соединений
  иначе «протечёт» контекстом).
- Текущий стек уже на JPA / Liquibase / Testcontainers-PostgreSQL.

## 6. Расчёты: с фронта на бэк

Сейчас бэкенд отдаёт сырые ячейки и политики, а фронт сам применяет штрафы
(`usePenalty`), вклад посещаемости, подсветку и считает итог (`useFinalVerdict`).
В платформе так нельзя: колонку «итог» добавляет другой плагин, экспорт и
будущий кабинет студента должны видеть те же цифры.

Конвейер балла участника в пространстве:

```
grading: сырой балл ячейки
   └─► ScoreModifier* по order (penalties: штраф/бонус по lessonsOffset)  ─► итоговый балл ячейки
сумма ячеек + ScoreContributor* (attendance-score: баллы за статусы)       ─► балл участника
final-assessment: банды по баллам/процентам + допуски заданий
                  + гейт по посещаемости (AttendanceApi, если включён)     ─► отметка
```

- Каждая ступень возвращает не только число, но и **пояснение** («−2: сдано на
  3 занятия позже») — фронт показывает его в подсказке ячейки, как сейчас.
- Расчёт детерминирован и без побочных эффектов → легко покрывается
  юнит-тестами; текущие composables дают готовые тест-кейсы.
- Кешировать не нужно на старте: группа × предмет — сотни ячеек. Если
  понадобится — материализованный итог, инвалидируемый событиями.

## 7. План перехода

Переписывать всё сразу не нужно — плагинную форму можно получить пошагово из
текущего бэкенда (strangler):

1. **Модули.** Разложить бэкенд на модули по будущим плагинам, включить
   `ApplicationModules.verify()`, убрать прямые обращения к чужим репозиториям.
2. **Расчёты на бэк.** Перенести `usePenalty`/`useFinalVerdict`/подсветку в
   сервисы, фронт оставить только отображать. Полезно и без платформы.
3. **Ядро данных.** `core.org`, `core.space` (= subject), `core.entity` с
   бэкфиллом существующих id; составные FK.
4. **Таблицы.** `TableProvider` для посещаемости (самая простая), затем журнал
   оценок с `ColumnContributor` итога; фронт — `<PluginTable>`.
5. **Гранты.** Перевести `teacher_subject_permission` в `core.grant` с
   измерениями от `people`/`schedule`.
6. **Маркетплейс.** Включение/выключение плагинов в пространстве; маршрутизация
   и меню по списку включённых.

## 8. Объём для ВКР и как его показать

Минимум, который доказывает концепцию:

- ядро: org/space, entity registry, plugin registry, extension points, table
  framework (read + patch), гранты с областью;
- плагины: `people`, `schedule`, `attendance`, `grading`, `penalties`,
  `final-assessment` (`check-in`, `highlight`, `attendance-score` — по
  остатку времени, они уже есть в VKR как функциональность);
- маркетплейс: включить/выключить с проверкой зависимостей.

Демонстрация (продолжение текущего демо-режима):

1. Выключить `penalties` → баллы в журнале и итог пересчитались, данные на месте;
   включить обратно → вернулось.
2. Попытаться выключить `schedule` → отказ: от него зависят `attendance`, `grading`.
3. Подключить альтернативный `teams` вместо `people` → журнал посещаемости
   работает без изменений кода `attendance` — главный аргумент за §4.
4. Преподаватель с грантом «группа X, только практики» видит и редактирует
   только свои ячейки во всех таблицах всех плагинов.

## 9. Связь с прототипом маркетплейса

В ветке `feat/sharp-euler-ws2bro` есть другой подход: маркетплейс на стороне
Nuxt, плагины ставятся во время работы — декларативные (JSON-таблица с
формулами над датасетом `students`) и код-плагины (ES-модуль с `setup(sdk)`).

Эти подходы не конкурируют, а занимают разные уровни:

| | Встроенные плагины (этот документ) | Расширения (прототип) |
|---|---|---|
| Кто пишет | мы | мы или кафедра |
| Где живут | бэкенд-модуль + Nuxt layer, в сборке | загружаются во время работы |
| Данные | свои таблицы в БД, запись | только чтение готовых данных |
| Пример | `attendance`, `grading` | «зона риска», рейтинг БРС, аналитика группы |

Если оба уровня остаются, расширения должны читать данные не из
захардкоженного датасета `students`, а через Table Framework (`TableResponse`
любой включённой таблицы) — тогда они автоматически уважают гранты и работают
с любым набором плагинов.

## 10. Риски

| Риск | Чем грозит | Что делаем |
|---|---|---|
| Ядро «протекает» предметными понятиями | теряется смысл платформы | правило ревью: в `core` нет слов из учебного набора; §8 п.3 как тест |
| Table Framework не покрывает реальные таблицы | плагины обходят его своими эндпоинтами | начать с двух самых сложных таблиц VKR (оценки, посещаемость) и выводить контракт из них |
| Гранты с областью тормозят на больших таблицах | медленные журналы | разрешать область один раз в `AccessContext`, фильтровать SQL-ом, а не построчно |
| Объём работ больше срока ВКР | недоделанная платформа | §7 даёт полезный результат на каждом шаге; §8 — явный минимум |

## 11. Открытые вопросы

1. Нужен ли кабинет участника (студента). Модель уже позволяет
   (`people.member.user_id`), но это отдельный UI и отдельная модель прав
   («видит только свои строки»).
2. Нужны ли пользовательские таблицы без кода (альтернатива из §4) или хватит
   расширений уровня прототипа (§9).
3. Перенос между пространствами: копировать настройки и занятия предмета на
   новый семестр — функция ядра (копия `space_plugin`) или каждого плагина
   (`SpaceCloner` как ещё одна точка расширения).
4. Аудит: достаточно общего журнала `core.audit` или журнал оценок требует
   полной истории ячейки с отменой.
